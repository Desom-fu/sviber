# sviber

Your task is to develop a chart editor for Sunniesnow called sviber.

Further instructions will be given in new versions of this prompt file,
and you can diff the new version of this file with the older versions to see what new instructions are added.
For instructions given outside this prompt file, if they contradict with what have been given in this prompt file,
inform about the contradiction and ask for clarificastion before proceeding.

## Overview

Sunniesnow is an open-source rhythm game running on web.
The website is at <https://sunniesnow.github.io>.
The game is live at <https://sunniesnow.github.io/game-unstable>.
There is also an old version that is live at <https://sunniesnow.github.io/game>,
but absolutely never refer to it because it is old.

The source of <https://sunniesnow.github.io> is at `..`.
It is a Jekyll project.

The source of Sunniesnow is at `../game-unstable`.
It is mostly just plain HTML and JavaScript.
There is a non-functional chart maker called sunniesnow-maker, whose source is at `../maker`.
I will ask you to copy some UI designs from Sunniesnow and sunniesnow-maker,
but ultimately you need to start from scratch,
and sviber is intended to completely replace sunniesnow-maker.
You should also follow the coding style and similar directory structures as those projects:
all JavaScript source codes (except tests, service worker, and `node_modules`) should live in `js`,
all SVG files should live in `svg`, all JSON data (except manifest) should live in `json`, etc.

The chart format of Sunniesnow is documented in `../doc/chart.md`.
You are not required to implement editing every feature of this chart format.
In other words, charts that are possible to have been created by sviber are a strict subset of all possible charts accepted by Sunniesnow.
The only types of events that you need to support editing are
`tap`, `hold`, `drag`, `flick` (with only one angle), `bgNote`,
`bigText`, and all background pattern events (`grid`, `turntable` etc.).

All coordinates that are mentioned in this document are in the chart coordinate system.
For the definition of the chart coordinate system,
see `../doc/chart.md`.

For better maintainability, a single JS file should not exceed 1000 lines.

## Technical notes

You will be writing plain HTML, JavaScript, and CSS.
Some parts of the editor are PixiJS apps, and you should load PixiJS v8 by fetching it from JsDelivr.
Other JS dependencies should be fetched in the same way.
The live webpage should still be usable offline by using service worker.
You can refer to Sunniesnow (`../game-unstable`) for a sample dependency and cache management.
Ignore the fact that sviber is inside a Jekyll project
(so no frontmatters).

The project will both be live on Sunniesnow's website
and be able to be used as a standalone desktop app through NW.js.
The online webpage version can also be installed as a PWA.
Therefore, you should also put a `package.json` file.
To make the app work offline, fetch the dependencies to `node_modules` using `npm`,
and load the dependencies from there.
Notice that `node_modules` will be ignored by the Jekyll site builder,
so the live webpage should still load dependencies from CDN.
Add a build script that builds the NW.js app,
and the script downloads all necessary assets (such as fonts for note texts) so that the app can work fully offline.
The app should also be able to launch in the source repo by `nw .` command (or some npm script)
for convenient testing.

For some mouse dragging operations, add the mouse event listeners to `document` or `window` instead of just the canvas
because the mouse up event can be missed if the user dragged the mouse outside the canvas.

Do not put `.ico` format or `.png` format icon in the source repo.
Generate it from the SVG icon in the build script of the NW.js app.
They should also be present in the source directory after running the build script
so that `nw .` can work.
For the webpage, just assume that the user's browser supports SVG icon.

All files generated by npm scripts must be put in `.gitignore`.

Write a `default.nix` file that defines a function so that it can be used with the `callPackage` function
of nixpkgs to get the package of sviber the NW.js app.
Write a `flake.nix` file that references `default.nix` to make the package its default package output,
and it uses `nixos-unstable` channel of nixpkgs as input.
Note that since both the build script and the Nix package needs hashes and URLs of fonts,
you can put the data in a JSON file in `json` dir and load the same data from different places.

## UI elements and UX design

The UI/UX should resemble a general desktop app for content creation.

All UI/UX designs should adhere to practical purposes but not asthetic purposes.
For example, the title bar of a popup form should have bold texts to indicate that it is a title,
and the title bar should also have a gray background indicating the part of the popup menu that can be interacted to drag it by mouse.
However, the title bar should not have rounded borders or distracting colors,
which are useless from a practical point of view.
This principle of design has been reflected in Sunniesnow and sunniesnow-maker,
and you should follow it.

For any reasonable window size, you should make sure that every main UI elements (such as the menu bar and the tooltip bar) are visible without scrolling.

### Menu bar

At the top of the window, there is the menu bar.
The top level menu items are directly listed on the menu bar, including "File", "Edit", etc.

When you click a top menu item, a drop-down submenu appears with a list of submenu items.
Every top level menu item can also be accessed by using <kbd>Alt</kbd> plus some letter key as a keyboard shortcut.
One letter in the menu item should be highlighted with underline to indicate which letter key is used in the keyboard shortcut.
There is visual feedback (darken background color) when the menu item is hovered.
The drop-down submenu disappears when the user clicks elsewhere
(in which case the clicked UI element will not respond to the click if there is any element being clicked).
If the mouse cursor moves to another item on the menu bar when the submenu of one menu item is shown,
the submenu appears for the new menu item,
and the submenu disappears for the old menu item.

In the submenu, there are horizontal separators that split the items to make them look more organized.
The user can trigger submenu items by clicking with mouse.
Alternatively, the user can navigate through the submenu items through up and down arrow keys or the tab key,
and then the user can trigger a submenu item by hitting spacebar or the enter key.
Some submenu items have keyboard shortcuts that can be used to trigger it without opening the drop-down menu.
The keyboard shortcut is documented on the submenu item.
Some submenu items have an icon, and the icon is shown at the left of the item if there exists one.
There is visual feedback (darken background color) when the menu item is hovered.
A tooltip pops up when the menu item is hovered (`title` attribute of the DOM element), and the tooltip should match the one shown in the [tooltip bar](#tooltip-bar).

You should copy the UI/UX design of the menu bar from sunniesnow-maker.
You do not have to copy the exact codes, but what you produce should look similar to it.
Notice that the UX of sunniesnow-maker does not exactly match what is documented here.
You should stick to what is specified in this document.
I will refer to icon files in sunniesnow-maker later, but you need to copy them into sviber
instead of literally use the link as is.

and the tooltip bar shows the tooltip that matches the tooltip of the menu item.
Notice that the popping up text (matches menu item text plus keyboard shortcut)
and the tooltip text (matches menu item tooltip) are different.

When a tool bar item is hovered and when it is clicked, there is visual feedback in the background color.

### Chart selection

To the right of the tool bar, there is a chart selection widget
that allows the user to switch between different charts in a project in a drop-down selection.
The format of each option is `${difficultyName} ${difficulty}${difficultySup}`,
and the difficulty name part is colored with `difficultyColor`.
The width of the selection widget should be just enough to contain the text,
and there is a maximum width that it should not exceed.
There are no other interactable buttons in the chart selection view.

Switching charts prompts saving the current chart if there are currently unsaved changes.

This widget is only present in the NW.js app, not on the webpage.

### Timeline

The timeline is a PixiJS app.
It is a separate PixiJS app from the main editor field.
It includes three parts: the waveform,
the channels, and the scroll bar.
There are vertical beat lines that are shown across the waveform and the channels.
The timeline has a black background.

You can copy the UX logic of the timeline from sunniesnow-maker.
You do not have to copy the exact codes, but what you produce should look similar to it.
Notice that the UX of sunniesnow-maker does not exactly match what is documented here.
You should stick to what is specified in this document.

#### Waveform

The waveform is a graphical representation of the current music.
The waveform is shown in a gray color.
It does not overlap with the channels in space.

For each beat line at $t$ (in beats), if $t-b$ is an integer
(where $b$ is the time in beats of the latest bar line before (inclusive) $t$),
a beat number shown at the place of the waveform,
but the number should be small so as not to interfere with the visual appearance of the waveform.
The number is simply the integer if it is an integer,
but it is written as integer plus numerator slash denominator format if it is not an integer.

If there are two A-B loop marks,
draw a translucent filled blue rectangle to cover the waveform,
spanning from the A mark to the B mark.

Whenever there is a BPM change, the place where the BPM changes has a purple number to indicate the BPM.
Show only the number.
For example, when the BPM changes to 120, just show "120", not "120 BPM".
Double clicking the BPM number can show a [popup form](#popup-form) to edit the BPM changing event.
The popup form should have identical fields as the one shown in [BPM change](#bpm-change),
but with the initial values filled with the current properties of the edited event.

There is a bright yellow vertical line shown on the waveform to indicate the current time.
Clicking or dragging on the waveform sets the current time at the mouse position, snapping to beat subdivisions.

Currently, the implementation of the waveform in sunniesnow-maker is poor in performance.
If a several minute long audio is loaded, the waveform can take a minute to be drawn.
Try to overcome this technical problem while still ensuring that the waveform can be zoomed up to visible individual samples.

#### Channels

Each channel is a series of events,
possibly being `tap`, `hold`, `drag`, `flick`, `bgNote`, `bigText`, any one of the background patterns, and `comment`.
The possible events do not include BPM changes because they are not real Sunniesnow events,
and the BPM change events are shown in the [waveform](#waveform) instead of the channels.

At the left, for each channel, the name of the channel is shown.
The name is bright yellow for the current channel or is otherwise light gray.
The name is translucent if the channel is inactive.

As the total number of channels can change
(through [create channel above](#create-channel-above), [delete channel](#delete-channel), etc.),
the total height of this part should also change.
When there are more than 3 channels, do not increase the height further
but show a vertical scroll bar to scroll through the channels.
The user can scroll through the channels vertically by interacting with the vertical scroll
or using the mouse wheel while holding <kbd>Shift</kbd>.
The latter interaction is always available as long as the mouse is not in a scrollable DOM element,
even if the mouse is not in the timeline canvas.

Whenever a chart is being edited in sviber, there is a special channel called the current channel.
A bright yellow vertical line is shown on only the current channel but not on other channels.

There is a horizontal line between every two adjacent channels to separate them visually.
The line should be colored dark grey so as no to be too distracting on the black background.

Every event is shown as an icon.
For `tap`, `hold`, `drag`, `flick`, and `bgNote`, just show the note body
(for `flick`, do not show the arrow part),
including the note text if there is any.
For `bigText`, use `../maker/svg/icons/create-bg-pattern.svg`.
For background patterns, devise your own design of icons, inspired from how they show up according to
`../game-unstable/js/ui/event/bg-pattern/*.js`.
For `comment`, devise your own design of an icon.
The colors of the icons must be very distinguishable from that of selected events (red).
For events with a duration, including `hold`, `bigText`, `bgNote`, and background patterns, show a tail to indicate the duration.
Check how Sunniesnow renders a tail for hold notes when the user setting `scroll` is `true` to inspire your design of tails.
Specially, for `bigText`, show the contents of the texts on the tail.

Notice that multiple simultaneous events may be in the same channel,
in which case their appearance should be shifted vertically so as not to completely block each other visually.
However, they should appear partially overlapping to save space.
This is UI design is similar to the timeline in the chart editor in osu!.
The drawing order of the events follows the order in which they are stacked vertically,
with the event stacked at the bottom being drawn at the top.

If an event is contained in a `group` event, draw a circle around its event icon with the color of the `group` event.
The circle needs to be larger than the event icon.
If it is inside a nested `group` event, for each `group` event that contains it directly or indirectly, draw a circle.
The circle for the outer `group` event is larger than the circle for the inner `group` event.

If the channel is deactivated, the events shown on it becomes translucent.
User interactions with this channel, including selecting events,
dragging events, and setting as the current channel, are also disabled on an inactive channel.
This is useful as sometimes there are so many simultaneous events in a channel
that it blocks the user from selecting adjacent channels without clicking on the events,
in which case the user can deactivate the channel with many events to operate on other channels.

Events that are connected by one tip point appear connected by a thick translucent white line.
Additionally, there is an additional segment of thin dark yellow line emanating from the first event connected by the tip point,
pointing in the direction from which the tip point flies in to the first event.
This additional segment is very short
(slightly longer than the radius of the event icon in the timeline)
and is independent of the horizontal zooming of the timeline
as this segment only needs to indicate the direction but
not the time of the tip point spawn.
For example, if a tip point spawns below the first event that it connects to,
then the additional segment points down from the event icon in the timeline.
It is drawn behind the event icons so as not to block the event icons visually.

When the user clicks an event (including its tail if it has one),
select that event without changing the current time or the current channel.
If the event is contained in a `group` event, select the `group` event instead.
Add the event to selection without deselecting previously selected events if the click is made while holding the <kbd>Ctrl</kbd> key.
Remoeve the event from the selection without affecting other selected events if the click is made while holding the <kbd>Alt</kbd> key.

When the user double clicks on an event contained in a `group` event,
temporarily allow selecting events in this group and select the event.
The group entering can only happen for one level at a time.
The group entering ends as soon as no events directly or indirectly contained in it are selected.

When the user clicks somewhere on a channel without clicking an event,
the current time and the current channel is changed accordingly,
and all selected events are deselected.
This operation does not modify the selection of events.
The current time is snapped to the nearest beat subdivision instead of being literally at where the user clicks.

When the user press down the mouse left button on a channel without touching an event and drag the mouse,
a rectangular selection region is formed and visibly drawn,
and all events in the region are selected.
A `group` is considered in the region if any event contained directly or indirectly in the group is inside the region.
This does not change the current time.
Notice that there needs to be a small threshold for the mouse move to trigger the selection mechanism,
otherwise it is regarded as a click to change the current time and the current channel.
The selection changes on live while the selection region changes as the user moves the mouse
until the user releases the mouse to finish selecting the events.
The drawn selection region is immediately disposed when the user releases the mouse.
Whether an event is selected is determined by whether the center of the event icon is inside the selection region.
If <kbd>Ctrl</kbd> is held while doing so, add the events to the selection without deselecting.
If <kbd>Alt</kbd> is held while doing so, remove the events from the selection.

When the user clicks somewhere on a channel while holding <kbd>Shift</kbd> key
(whether he clicks on an event or not),
change the current time and the current channel accordingly,
and also select all the events between the previous time and channel and the current time and channel.
The channel range is inclusive on both ends, and the time range is inclusive on the beginning and exclusiving on the ending.
For example, suppose that the current time is at beat 1 and that the current channel is channel 2.
Then, the user clicks at beat 5 at channel 4 while holding <kbd>Shift</kbd>.
The editor should now select all events that are in channel 2, 3, 4, and whose beat is between 1 (inclusive) and 5 (exclusive).
Add those events to the selection without deselecting previously selected events if the user is also holding <kbd>Ctrl</kbd>
Remove those events from the selection if the user is also holding <kbd>Alt</kbd>.

Selected events appear with a bright red tint.
Additionally, a selected `group` event appears with a rectangle enclosing the events directly or indirectly contained in it,
and the rectangle uses the same color as the user-set color of the `group` event.

Selected events can be dragged with mouse to be moved to other channels and time.
There is a small threshold over which the mouse must move a distance to trigger the event dragging.
For this mechanics, selecting a `group` event is effectively equivalent to selecting
all events contained directly or indirectly in it.
For moving a single event, it can be moved by the same mouse down as the click that selects the event.
If the events are moved while <kbd>Ctrl</kbd> is pressed,
make a copy of the events at the moved place
and leave the original events unchanged.
If all selected events are simultaneous, the events can only be moved to snap to beat subdivisions;
otherwise, the events can only move by integer multiples of beat subdivisions.
For example, if all selected events are simultaneous and are at beat $2+1/2$
and the current subdivision is $1/3$ beats,
then these selected events can only be moved to beat $n/3$, where $n$ is an integer.
If all selected events are not simultaneous, and the $i$th selected event is at beat $b_i$,
and the current subdivision is $1/3$ beats,
then the $i$th event can only be moved to beat $b_i+n/3$,
where $n$ is an integer and is the same for all $i$.

For each selected event with a duration, a handle marked as a white diamond appears.
The size of the handle is smaller than the event icon
(otherwise the user cannot click an event icon if an end time handle blocks it).
The user can use mouse to drag the handle to change the end times of the events with durations.
For this mechanics, selecting a `group` event is effectively equivalent to selecting
For each event, its end time must not be smaller than its time;
if its event type additionally does not allow zero end time, its end time must be strictly larger than its time.
If the end times of all selected notes with durations are the same,
the end times can only snap to beat subdivisions;
otherwise, the end times can only be shifted by the same integer multiple of beat subdivisions;
this behavior is similar to dragging events in time, described in the previous paragraph.

The user can use <kbd>Alt</kbd>+<kbd>Up</kbd> or <kbd>Alt</kbd>+<kbd>Down</kbd>
to change the current channel to the one above or below the original one.
The user can also use <kbd>Alt</kbd> plus number keys to select the chrrent channel.
For example, the first channel can be selected with <kbd>Alt</kbd>+<kbd>1</kbd>,
the second channel can be selected with <kbd>Alt</kbd>+<kbd>2</kbd>, etc.
The user can also use <kbd>Alt</kbd>+<kbd>0</kbd> to select the last channel.
If there are enough channels to make a vertical scroll bar appear,
when the user selects the current channel using keyboard shortcuts,
scroll it to make sure the current channel is visible in the timeline.
These operations do not exit the event creation mode.

#### Beat lines

There are vertical lines that span the waveform and the channels.
Those lines indicates the position of beat subdivisions.
For a time $t$ measured in number of beats, there is a beat line at $t$ if $\left(t-b\right)s$ is an integer,
where $b$ is the time (in beats) of the latest bar line before (inclusive) $t$,
and $s$ is the current beat subdivision.
Especially, the beat line is thickened if $t=b$.
The color of the beat line is determined by the denominator in the simplified fraction representation
of the rational number $t-b$ according to the following table:

| Denominator | Color |
|-|-|
| 1 | red (#ff2e59) |
| 2 | blue (#3086ff) |
| 3 | green (#50a226) |
| 4 | yellow (#ff9d3d) |
| 8 | purple (#d567ff) |
| others | cyan (#00e0ad) |

Beats can be negative.

The default beat subdivision is 1/2 beats.

At A-B loop marks, bright blue vertical lines are drawn regardless of the current subdivision.

#### Scroll bar

The scroll bar is horizontal.
There are three major points in time that should be marked on the scroll bar:
the beginning of the visible range, the end of the visible range, and the current time.
When there are A-B loop marks, they are also marked on the scroll bar.

A bright yellow vertical line indicates the current time.
The user can interact with the line using mouse to move it to other time across the music to change the current time.
During the interaction, the current time is always snapped to beat subdivisions.

Two green vertical lines indicate respectively the beginning and the end of the visible range.
The visible range is the range where the waveform and the channels are visible.
One green horizontal line connects the two vertical lines.
The user can interact with either green vertical lines to move it to change the visible range.
The user can interact with the horizontal green line to move both ends.

If there is at least one A-B loop mark, draw a blue vertical line indicating the position for every mark.
If there are two A-B loop marks, draw a translucent filled blue rectangle indicating the range between the two marks.
In any case, they are not interactable on the scroll bar.

The mouse interaction priorities: bright yellow line > two vertical green lines > horizontal green line.

The current time can be outside the visible range.
The smallest possible value of the current time and the beginning of the visible range is the time of beat 0 or the time when the music begins, whichever is smaller.
The largest possible value of the current time and the end of the visible range is the time when the music ends
(in the edge case where there is no music loaded,
use 10 seconds after the end of the last event as the bound).

The user can also use the mouse wheel to navigate over the timeline,
which changes both the current time by one beat subdivision.
The current time increases by one subdivision if the user scrolls down,
and the current time decreases by one subdivision if the user scrolls up.
When the user increases the current time by using the mouse wheel,
if originally the current time is outside the visible range
or is smaller than the center of the visible range,
then this action does not change the visible range;
otherwise, also change the visible range by one beat subdivision.
When the user decreases the current time by using the mouse wheel,
if originally the current time is outside the visible range
or is greater than the center of the visible range,
then this action does not change the visible range;
otherwise, also change the visible range by one beat subdivision.
The mouse wheel navigation works anywhere as long as the mouse is not in a scrollable DOM element.

When the user uses the mouse wheel while holding the <kbd>Ctrl</kbd> key,
the visible range shrinks/zooms in (if scrolling up) or enlarges/zooms out (if scrolling down) without changing the center of the visible range.
If the enlargement will make the visible range exceed the bounds set by the music,
change the center so that the visible range is still within bounds.

When the user clicks and drags with mouse in the timeline while holding <kbd>Ctrl</kbd>+<kbd>Space</kbd>,
pan the visible range following the mouse.
This does not change the current time.
This operation still works if the visible range lock is on.

When the music is [playing](#play-pause) or [playing in reverse](#play-in-reverse), the current time change accordingly.
The current time is always at the playing progress, not snapped to beat subdivision
(this is the only case where the current time is not snapped).
When the music is playing normally, if the current time is not in the visible range or smaller than the center of the visible range,
do not move the visible range while playing;
otherwise, move the visible range while playing so that the current time marker on the waveform and the current channel does not appear moving.
When the music is playing in reverse, if the current time is not in the visible range or is larger than the center of the visible range,
do not move the visible range while playing;
otherwise, move the visible range while playing so that the current time marker on the waveform and the current channel does not appear moving.
If the visible range is moving while the music is playing to the point where the visible range is exceeding the music bounds, stop moving the visible range in this case.
When the music playing stops, if the checkbox for seeking back after music playing is checked,
change the current time and the visible range back to when the music started playing;
otherwise, the current time is snapped the nearest beat subdivision, and the visible range does not change.
If the user tries to change the current time by interacting with the scroll bar while the music is playing or playing in reverse,
pause the music until the interaction finishes and restart playing from the new current time.
If the user tries to change the visible range while the music is playing or playing in reverse,
make the change happen without interfering with the playing.

When the user clicks on the scroll bar outside the visible range bar,
the visible range moves by the length of the visible range.
In other words, if the visible range is initially from $t_1$ to $t_2$,
if the user clicks to the right of the visible range bar,
the visible range is shifted by $t_2-t_1$;
if the user clicks to the left of the visible range bar,
the visible range is shifted by $t_1-t_2$.
If the current time is initially within the visible range,
then the current time is shifted by the same amount;
otherwise, the current time does not change.
The user can also use <kbd>PageUp</kbd> (to shift the visible range by negative amount)
and <kbd>PageDown</kbd> (to shift the visible range by positive amount) to do the same operation.

Clicking the scroll bar has higher priority than clicking events in channels.

### Status panel

The status panel is located to the right of the timeline.
It does not need a panel title.
It shows the following information:

- Time: the current time, in the format of minute, colon, second rounded to 3 decimal places.
- Beat: the current beat, in the format of integer part plus numerator slash denominator.
  The denominator is always the same as the current subdivision denominator.
  In other words, the fraction is not simplified to have coprime numerator and denominator.
- Speed: the current playback rate.

For example, it can be:

```
1:07.814
121+0/4
0.5
```

Below the basic information, there are some basic control options,
all of which are checkboxes.
Each checkbox has an icon but no texts as its label.

- Lock visible range (`lock-visible-range.svg`): when checked, the visible range can only be changed by interacting with the timeline scroll bar or the keyboard,
  but cannot be changed by [playing music](#play-pause),
  [playing music in reverse](#play-in-reverse),
  or [seeking](#seek-forward-seek-backward) using menu items or mouse wheel.
  The visible range can still be changed by using <kbd>Ctrl</kbd> plus mouse wheel. This is false by default.
- SE (`se.svg`): global toggle of note SE when playing music. SE of notes in inactive channels are not played in any case. This is true by default.
- Seek back after playing (`seek-back-after-playing.svg`): when checked, after the music playing stops,
  the current time is changed back to when the music started playing. This is false by default.
- Metronome (`metronome.svg`): when checked, play a synthesized percussion sound every time when it is an integer number of beats from the latest bar line before (inclusive) that time.
  The metronome must be perfect in sync with the music, using the same method as how note SE can be made perfect in sync with the music.
  You need to invent your own synthesized sound effect for the metronome.
  It needs to be sharp, clear, and short, and is distinct from all note SE.
- Show grouping in timeline (`show-grouping-in-timeline.svg`): when checked, show circles enclosing event icons in the timeline and the scroll view
  that indicate the grouping of events. Checked by default.
- Show grouping in main field (`show-grouping-in-main-field.svg`): when checked, show circles enclosing events in the main editor field

#### Background

Refer to the implementation of the background in Sunniesnow.
See `../game-unstable/js/ui/gameplay/Background.js`.

The background image should be the an image set by the user.
If the user did not set one, use pure white.
Then, take that image and blur and darken it,
according to the default settings in Sunniesnow.
Render the blurred and darkened to a texture and use that texture
instead of having a constant filter as a filter is heavy performance burden.
Note that the default white background must also be darkened, just like the "none" background handling in Sunniesnow.

#### Chart boundary

The chart boundary is a rectangle whose top left is at $(-100,50)$
and whose bottom right is at $(100,-50)$.

#### Events

The events, including notes, bg notes, background patterns, and also tip points (although they are not actual events),
appear exactly like they should at the current time
as per the implementation in Sunniesnow
(except comments because Sunniesnow does not have comments;
comments are simply not rendered in the main field),
including every detail of note bodies, shrinking circles, etc.
See `../game-unstable/ui/event/**/*.js` for references.
However, you do not need to make the code as complicated as Sunniesnow
because there will not be too much user settings that can tweak the appearances,
and you do not need to support `timeDependent` and `filters`.
One important point is that, when the current time is exactly at the time of an event,
render the `active` phase or `hold` phase (according to whether the event has duration)
instead of the `fadingOut` phase.

Additionally, only when in event creation mode,
for each note or bg note, draw a translucent hollow circle (for notes)
or hexagon (for bg note) with the same size after (but not when equal to) the end time of the event,
and this shape becomes more and more transparent until $1/s$ seconds after the end time when this shape should fully disappear,
where $s$ is the animation speed preference value.
You do not need to concern about how these shapes should interact with user action
because the user cannot interact with events during event creation mode anyway.

Additionally, if a movable event in an active channel is contained in a `group` event,
draw a circle around it with the user-set color of the `group` event.
The circle needs to be larger than the note body.
If it is inside a nested `group` event, for each `group` event that contains it directly or indirectly, draw a circle.
The circle for the outer `group` event is larger than the circle for the inner `group` event.

Additionally, if a movable event in an active channel is attached to the selected snappee,
draw a circle around it with the user-set color of the snappee.
The circle needs to be larger than the note body.

The drawing order of the events follows the following rules,
each rule having lower priority than the previous rule (the first rule has the highest priority).
(1) The background pattern must be below the bg notes,
and the bg notes must be drawn below any other types of movable events.
(2) Events later in time must be drawn above events earlier in time.
(3) The drawing order of simultaneous events follows the order of their channels,
with the channel ordered at the top being drawn at the bottom.
(4) The drawing order of simultaneous events in the same channel
follows the order of stacking in the channel in the timeline interface,
with the event stacked at the bottom being drawn at the top.

Events in inactive channels, along with the tip points that connect them, are neither visible nor selectable in the main editor field.

When the user clicks an event, select it.
If the event belongs to a `group` event, select the `group` event instead
(selecting a `group` event is different from selecting all events belonging to the group;
for example, selecing a `group` event containing a `flick` event does not make the `flick` event appear with a handle
to change its angle).
The hit region of an event is its body (for `hold`, not including the hold halo; for `flick`, not including the arrow),
which is a circle region
(specially, it is a hexagon region for `bgNote`).
Background patterns, `bigText`, and `comment` cannot be selected in this way
(the user can only select them from the [channels](#channels) in the timeline).
Clicking while holding <kbd>Ctrl</kbd> adds the note to the selection without deselecting previously selected events.
Clicking while holding <kbd>Alt</kbd> removes the note from the selection.
Selection operations are also items in the history panel, but do not add them as history items if the selection does not change.

A handle appears at the tip of the arrow at each selected `flick` event.
The user can interact with the handle using the mouse to change the direction of all selected `flick` events.
When changing the direction in this way, the angle is snapped to integer multiples of $\pi/4$ if there is only one selected `flick` event;
otherwise, all angles can change by integer multiples of $\pi/4$ without changing their differences.
This snapping does not affect directly changing angles in the inspection panel.

Selected events and events contained directly or indirectly in selected `group` events appear with a bright red tint.
Even if some selected event is not visible at the current time,
its red tint or outline is still visible to indicate that something not visible is being selected.
A selected `group` event (not including those nested inside selected `group` events) additionally appears with a rectangle
bounding all events directly or indicrectly contained in it,
and the rectangle uses the user-set color of the `group` event.

When there is only one movable event (i.e., note or `bgNote`)
and possibly unmovable events (i.e., `bigText` and background patterns) in the selection,
the user can drag the selected movable event with mouse to change its position.
The drag can be done by the same mouse down as the one that selects this event.
The event cannot be moved outside the chart boundary
(for a `group` event, any event that it contains directly or indirectly cannot be moved outside the chart boundary,
even for those events that are in inactive channels).
The movement automatically attaches the event to a snappee if it is moved near a snap point of some activated snappee.
Dragging a `group` event in this way changes the position of the `group` event itself
and recursively the positions of all movable events directly or indirectly contained in the `group` event.

When there is only one tip-pointable event (i.e., note) in the selection,
whose tip point spawn type is drop or chain
or which inherits a drop spawn type from a previous tip-pointable event in the channel,
then a handle appears that the user can drag using the mouse to change the spawn position.
The spawn position can snap and attach to snap points if the tip point spawn has absolute position.
If the tip point spawn has relative position,
the spawn direction is snapped to integer multiples of $\pi/12$,
and the spawn distance is snapped to integer multiples of 12.5.
The mechanics in this paragraph is only active when showing tip points are enabled.

When all selected movable events are attached to no snappees
or there is only one selected movable event,
the user can move them together by dragging with mouse.
The event that the user is directly interacting with can be attached to a snappee,
but only this one event will be attached
while all other together moved events are simply placed at the moved position without attaching.
The user can move selected events again if he attaches one event in the last move
but does not change the selection or only adds non-attached events to the selection,
despite that this case does not meet the condition of all movable events being non-attached.

When there is only one `group` event in the selection or when all selected `group` events are not attached to any snappee,
a crosshair circle handle, called the anchor, that the user can drag with mouse appears at the position of each `group` event.
Dragging the anchor changes the positions of all selected `group` events without changing the position of the contained events.
The anchor that the user directly interact with can snap and attach to snappees as usual
(while all other together moved anchors are simply placed at the moved positions without attaching),
but additionally it can snap (not attach) to movable events contained (not indirectly) in the `group` event.
Snapping to movable events in the `group` event has higher priority than snapping to snappees.
The user can move the anchors of the selected `group` events again if he attaches one anchor in the last move
but does not change the selection or only adds non-attached `group` events to the selection,
despite that this case does not meet the condition of all `group` events being non-attached.
The following few paragraphs about moving multiple selected movable events also apply similarly to
moving the anchors of multiple selected `group` events.

When there are more than one selected movable events
and all selected movable events are attached to the same rectangular mesh,
the user can move them together by dragging with mouse.
They are still attached to the mesh when being moved.

When there are more than one selected movable events
and all selected movable events are attached to the same radial mesh,
the user can move them together by dragging with mouse.
The movement is limited to rotation around the center of the radial mesh.
The events are still attached to the mesh when being moved.

When there are more than one selected movable events
and all selected movable events are attached to the same curve,
the user can move them together by dragging with mouse
by shifting them through the snap points on the curve.
They cannot be moved outside the curve because they are keep being attached to it.
However, if the curve is loop (its two ends are identified),
the movement can infinitely rotate the events along the curve.

If the user press down the mouse left button without touching an event,
make a rectangular selection region that the user can drag with the mouse to resize and that is visibly drawn.
Notice that there needs to be a small threshold for the mouse move to trigger the selection mechanism,
otherwise it is regarded as a click to deselect all events.
It selects all currently visible movable events whose positions are inside the selection region
(this does not concern the hit region of the events).
The selection is update on live until the user releases the mouse to finish the selection.
If <kbd>Ctrl</kbd> is held, add the events to the selection without deselecting.
If <kbd>Alt</kbd> is held, remove the events from the selection.

If the user double clicks an event contained in a `group` event,
temporarily allow selecting events contained in the `group` event and select the double clicked event.
This mode deselects the `group` event, which cannot be selected until the mode exits.
This temporary group entering can only happen for one level at a time,
so if an event is in a `group` event that is contained in a `group` event,
the user needs to double click it twice to actually select it.
The temporary group entering ends as soon as there are no selected events contained in the group.

If the user clicks and drags in the main field while holding <kbd>Shift</kbd>,
move all selected movable events just as how you should move them if the user is dragging them without holding <kbd>Shift</kbd>.
The difference is that this allows the user to drag events without
having to aim the mouse at one selected events
or having to avoid selecting other events.
If how the events are moved depends on which specific event the user is interacting with
(e.g., when all selected movable events are attached to the same curve),
handle the movement as if the user is interacting on the last selected event.
If there are no selected movable events but a snappee is selected when the user does this operation,
move the selected snappee (changing its transformation matrix).

#### Snappees

See [overview of snappees](#overview-of-snappees) to know about snappees.

Every snappee has a user-set color.
Draw the snappees with user-set color.
The lines should be thin enough so as not to distract the user.

The layer for drawing snappees is above that for the background patterns but below the notes (including `bgNote`).
The drawing order among snappees matches the order in the snappees panel,
with the top snappee in the order being drawn at the top.

For a rectangular mesh, draw a rectangular grid.
For example, if rectangular mesh is set to have 3 by 2 tiles,
then you need to draw 4 vertical line segments and 3 horizontal line segments to form a grid.
When a rectangular mesh is selected in the [snappees panel](#snappees-panel),
two handles appear, one at the top left corner and the other at the bottom right corner of the mesh.
The user can drag the handles with mouse to change the size and position of the mesh.
The handles can be snapped to other active meshes,
but they are not really attached but merely moved there.
In other words, if those other meshes are moved, the positions of the handles are not moved accordingly.
Opposed to events, the mesh handles may be moved outside the chart boundary.
Also, notice that the positions of the handles are after applying the transformation matrix,
so you need to invert the transformation matrix to actually get the correct new parameters of the snappee.
Such UX features of mesh handles are similar for other snappees,
so they are not repeated later.

For a radial mesh, draw circles and segments that connects the center to the outermost circle.
For example, if a radial mesh is set to have 3 by 2 tiles,
then you need to draw 3 line segments and 2 circles.
The circles need to be actual circles instead of broken lines connecting the snap points.
When a radial mesh is selected in the snappees panel,
two handles appear, one at the center, and the other at the outer end of one segment.
The user can drag the handles to change the position, size, and angle of the radial mesh.
The handles can be snapped to other meshes.

For a parametric mesh, connect every pair of nearest neighbors with straight line segments.
For example, for a parametric mesh with 3 by 4 points,
you need to draw 17 line segments:
connect $(x_{00},y_{00})$ with $(x_{10},y_{10})$ and $(x_{01},y_{01})$;
connect $(x_{11},y_{11})$ with $(x_{01},y_{01})$, $(x_{10},y_{10})$, $(x_{21},y_{21})$, and $(x_{12},y_{12})$; etc.

For a regular polygon curve, draw the regular polygon,
with dots highlighting the snap points on the sides.
Its handles are one at the center and one at a vertex.
They can be used toe change the position, direction, and size of the regular polygon.

For a B&eacute;zier curve, draw the B&eacute;zier curve,
with dots highlighting the snap points on the curve.
Notice that it needs to be drawn as a full curve, not a broken line connecting the snap points.
When it is selected in the snappees panel,
show handles at every control points of the B&eacute;zier curve
to change its shape and position.

For a circular arc curve, draw the arc,
with dots highlighting the snap points on the curve.
It has three handles, one at the center of the circle,
and two at both ends of the arc.
The one at the center can be used to move the position of the arc.
The two handles at the ends can be used to change the beginning and ending angle of the arc,
and they can only move along the circle.

For a pen curve,
draw the curve, with dots highlighting the snap points on the curve.
Notice that it needs to be drawn as a full curve, not a broken line connecting the snap points.
Its handles are all control points.

For a parametric curve,
use a broken line to connect every snap points,
with those points as nodes of the broken line.

A snappee can be double clicked to select all visible events that are attached to it.
Holding <kbd>Ctrl</kbd> while doing this adds them to the selection without deselecting.
Holding <kbd>Alt</kbd> while doing this removes them from the selection.

### Scroll view

To the left of the main editor field, there is the scroll view, which is also a separate PixiJS app.
It displays movable events as event icons, identical to the event icons used by the timeline.
Events contained in `group` events also have colored circles indicating the grouping just like in the timeline.
A selected `group` event also has a colored bounding rectangle just like in the timeline.

The placement of events in the scroll view is determined by their times and their x coordinates.
In the scroll view, the horizontal direction is the x direction,
and the vertical direction is the time direction (top has larger time than bottom).
The current time is always put at the same height near the bottom (the distance to the bottom is 1/4 of the height) of the scroll view
no matter what the current time is
so that the events appear scrolling vertically as the current time changes.
For movable events with durations (`hold` and `bgNote`),
vertical tails are shown to indicate their durations, similarly to the duration tails in the channels in the timeline.

Events in inactive channels are invisible in the scroll view.

Event icons for `bgNote` events are always behind event icons of other types.
For other cases, event icons of later times is in front of event icons of earlier times.

Events connected by the same tip point are connected by a thick translucent white line.
Additionally, the first event that a tip point connects to has a dark yellow thin line emanating from it
to indicate the direction from which the tip point spawns.
This is similar to the tip point spawn direction indicator in the timeline.

The visible time range of the scroll view is so that the vertical visual distance per unit time in the scroll view
is equal to the horizontal visual distance per unit time in the timeline
and that the current time is at a fixed visual height.
Stick to these principles even if that means the visible time range of the scroll view
may exceed the music time bounds.

The range of chart x coordinates that the scroll view shows is
the default play field width in Sunniesnow.

The scroll view also have beat lines, which are horizontal lines.
They use the same color scheme as the beat lines in the timeline.
The current time is marked with a bright yellow line.
At the left of the scroll view near every red beat line,
a red number is shown to indicate the beat number of that beat line.
At A-B loop marks, bright blue horizontal lines are drawn regardless of the current subdivision.
When there are two A-B loop marks, a translucent blue rectangle is drawn to cover the region between them.

When the user clicks and drags with mouse in the scroll view while holding <kbd>Ctrl</kbd>+<kbd>Space</kbd>,
pan the scroll view following the mouse by changing the current time.
If the visible range does not originally contain the current time or the visible range lock is on,
do not change the visible range; otherwise, change the visible range so that the visual position of the current time
in the timeline does not change.
The current time is not snapped to subdivisions while doing this operation,
but the current time is snapped to subdivisions after doing this operation if the music is not playing.

When the user clicks an event icon in the scroll view, select the event.

The region is disposed once the mouse is released.
If the user does the operation while holding <kbd>Ctrl</kbd>, add to selection without deselecting.
If the user does the operation while holding <kbd>Alt</kbd>, remove from selection.

## Overview of snappees

The word "snappee" is invented to call objects that define a set of points that a positioned event can snap its position to.
There are two major types of snappees: mesh and curve.
Both of them have more subtypes that I will introduce.

From a technical point of view, a snappee is just a set of points on the plane.
When the user moves something by dragging with the mouse,
it will automatically snap the position to a snap point on the snappee
if it is close enough (distance within 6.25 in the chart coordinate system).
If there are multiple snap points that are close, the closest point to the mouse cursor is snapped to.
If there are multiple closest snap points, the uppermost snappee (by the ordering in the snappees panel) gets the highest priority.

In [events creation mode](#tap-hold-drag-flick-bg-note)
or when [attaching](#attach),
snap points outside the chart boundary are not considered valid snap points that events can attach to.
However, sometimes due to floating point error, some snap points that should
mathematically be right at the chart boundary is numerically outside the boundary.
Therefore, the judgement of whether a snap point is within the chart boundary
should have a very tiny tolerance.
There is no tolerance for other cases of determining whether a position is inside the chart boundary.

The difference between a mesh and a curve is that snap points in a mesh are labeled by two indices while snap points in a curve are labeled by one index.
Specially, curves can be a loop (i.e., the first snap point identifies with the last snap point).
More generally, we can identify snap point $i$ with snap point $i+m$,
where $m$ is the number of snap points.
This is useful in some cases.
For example, when the user moves events from one snap point to another on a curve,
the events can be moved indefinitely along the curve if the curve is a closed loop;
on the ohter hand, if the curve has open ends,
the events cannot be moved past the ends.

Snappees can be transformed by some tools such as [free transform](#free-transform).
Such transformations are not implemented by directly changing the parameters of the snappees
but by composing a transformation matrix (2D affine transformation matrix with 6 degrees of freedom).
The transformation matrix can be manipulated independently of the snappee parameters.

Snappees can be active or inactive.
Inactive snappees are invisible in the main editor field,
and placing things in the main editor field does not snap to inactive snappees.

For new charts, a ectangular mesh from $(-100,50)$ to $(100,-50)$ with 16 by 8 tiles
is created and activated by default because it is commonly used,
and the user has the freedom to delete it.
Its name is "Playfield grid" by default if the editor is in English.
The default name is internationalized and is dependent on the editor language when the mesh is created.

### Rectangular mesh

The simplest snappee is the rectangular mesh.
Its parameters include the coordinates of its top left corner $(x_{00},y_{00})$,
the coordinates of its bottom right corner $(x_{mn},y_{mn})$,
the number of tiles in the horizontal direction $m$, and the number of tiles in the vertical direction $n$.

It is just a rectangular grid, and its snap points are the grid intersections
or the vertices of the tiles.
To elaborate, the snap points are
$$(x_{ij},y_{ij})=\left(x_{00}+\frac im(x_{mn}-x_{00}),y_{00}+\frac jm(y_{mn}-y_{00})\right),\quad
i=0,\ldots,m,\quad j=0,\ldots,n.$$

### Radial mesh

The radial mesh have these parameters:
the coordinates of its center $(x_{00},y_{00})$,
the radius of the outermost circle $R$,
the number of tiles in the azimuthal direction $m$,
the number of tiles in the radial direction $n$,
and the starting angle $\varphi_0$.
The snap points are
$$(x_{ij},y_{ij})=\left(x_{00}+\frac jnR\cos\!\left(\varphi_0+\frac im2\pi\right),y_{00}+\frac jnR\sin\!\left(\varphi_0+\frac im2\pi\right)\right),\quad
i=0,\ldots,m-1,\quad j=0,\ldots,n.$$

### Parametric mesh

For a parametric mesh, the expression of $x_{ij}$ and $y_{ij}$ are two user-input mathematical expressions
that can be parsed using [math.js](https://mathjs.org).

### Regular polygon curve

The regular polygon curve has the following parameters:
the coordinates of the center of the regular polygon,
the radius of the regular polygon,
the direction of one radius segment of the regular polygon specified as polar angle,
the number of sides $n$ of this regular polygon,
and the number of segments $m$ on each side.
There are totally $nm$ snap points on the sides of the regular polygon.

A regular polygon curve is naturally a closed loop.

### B&eacute;zier curve

The B&eacute;zier curve has one parameter $n$ for its degree,
$2\left(n+1\right)$ parameters for the coordinates of the control points,
and one parameter $m$ for the number of segments.
The snap points are the vertices of segments of the curve,
and the segments are determined by dividing the curve into $m$ segments with equal curve lengths.

After creating curve, open a popup form for editing its parameters.
The input is focused at the field for changing the number of segments.

### Pen curve

The pen curve can have many parameters.
It is the same as the curves produced by the pen tool in programs such as Inkscape.
It is composed of a bunch of connected B&eacute;zier curves
whose degrees are not larger than 3.
It has an additional parameter $m$ for the number of segments,
and the snap points are the vertices of the segments.
The segments have equal curve lengths.

[sscharter](https://github.com/sunniesnow/sscharter),
another charting tool for Sunniesnow,
has a tool to convert an SVG path to a set of points with equal curve length distance between them.
You can refer to its code, but you are encouraged to devise better algorithms.

After creating curve, open a popup form for editing its parameters.
The input is focused at the field for changing the number of segments.

### Parametric curve

For a parametric curve, snap points are user-input mathematical expression $(x_i,y_i)$.

or it is in plain Sunniesnow chart format.
In the former case, simply load the chart from the metadata and the `sviber` object in the JSON object,
ignoring the `events` array in the JSON.
In the latter case, sviber tries to import the plain Sunniesnow events as sviber events.
Most importantly, sviber events have time specified in terms of rational beat numbers,
while Sunniesnow events have time specified in float numbers in seconds,
and the plain Sunniesnow chart format does not have beat information.
Therefore, in this case, show a new popup form to ask the user to enter information to set up the beats:

- Offset
- Initial BPM
- Information of all BPM change events
- Largest denominator of beats of events

The offset and the initial BPM is the same thing as in [creating a new chart](#new).
The information of all BPM change events
is an array of BPM change events, with each event having data for the beat when the BPM change happens (in rational number)
and the BPM immediately after the BPM change.
The largest denominator sets an upper bound of the beats of the imported events.
All events are snapped to closest rational numbers of beats whose denominators do not exceed the value specified here.

Notice that sviber does not have placeholder events, but Sunniesnow heavily depends on placeholder events for tip points.
Importing goes as the logic explained as follows.
First, look at the `tipPoint` properties of all events and construct the tip point chains.
Put all events that are not connected by a tip point in the first channel and change their tip point spawn type to "none".
Then, for each tip point chain, do the following steps:

1. Delete events that are neither placeholder events
   nor sviber tip-pointable events (so, e.g., bg notes are removed from the chains).
   The events are just deleted from the tip point chain in this step of processing,
   not deleted from the chart.
2. If the first event is not a placeholder,
   add a placeholder event at the beginning that have the same position and time as the first event.
3. Repeatedly delete the first event of a placeholder until the second event is not a placeholder or the second event does not exist.
   In the latter case, stop the processing of this tip point chain and go to process the next one.
4. Delete all placeholder events except the first one.
5. Find the first channel that does not have any event after (inclusive) the second event in the chain
   and before (inclusive) the last event in the chain.
   If no such channel is found, create a new channel.
   Then, put all events in the chain except the first one into the found channel.
6. If there are only one non-placeholder event,
   set its tip point spawn type to "drop".
   Otherwise, set the tip point spawn type of the first non-placeholder event to "chain",
   and set that of all other non-placeholder events to "inherit".
7. Set the tip point spawn position and spawn time of the first non-placeholder event
   according to the position and time of the placeholder event relative to it.
   The spawn position type is relative (i.e., set position in distance and direction),
   and the spawn time type is in seconds.

Initially, the chart has no bar lines.
Note that bar lines in sviber are not conceptually equivalent to bar lines
that separate measures in western sheet music.
Instead, they are only necessary when actual music pulses are not at mathematically integer beats,
which often happen when a measure does not have an integer number of beats.

When snapping time to beat subdivisions, you need to consider bar lines.
A time that can be snapped to is one whose difference from the latest bar line before (inclusive) it
is an integer multiple of the beat subdivision.
For example, if the current subdivision is 1/2 and there is only one bar line at 1+2/3 beats,
then the times that can be snapped to are 0, 1/2, 1, 1+1/2, 1+2/3,
2+1/6, 2+2/3, 3+1/6, etc. beats.
They correspond to the [beat lines](#beat-lines) in the timeline.

If it is already in the event creation mode and it is for the event type of the triggered operation,
exit the event creation mode.
If it is already in the event creation mode but it is not for the event type of the triggered operation,
or if it is not in the event creation mode and there are no currently selected movable events,
enter the event creation mode of the correct event type.
If it is not in the event creation mode and there are currently selected movable events,
convert the selected events to this event type.
For example, the user can select a bunch of events and then hit <kbd>T</kbd>,
and all of them will be converted to taps.

In the event creation mode, a translucent event sprite will appear on the main editor field, indicating where the new event will be placed.
It follows the mouse.
It is generally at the same position as where the mouse points.
If the mouse is near (the distance threshold is 6.25 in the chart coordinate system)
a snap point, then it is at the nearest snap point
(in which case the placed event will be attached to the snap point).
If the mouse is outside the chart boundary, then it is clamped at the chart boundary.
In the status panel, information about the coordinates of the new event and which snappee (if any) the new event will be attached to is displayed.
The user can do the actual placing by clicking the mouse when he deems the translucent preview to be satisfactory.
This clicking will not trigger interaction with the main editor field (events selection etc.).
After placing the event, the current selection is updated to contain only this new event.
The event creation mode does not end after this, and the user can continue placing new events.

Hitting <kbd>Esc</kbd>, triggering most sub-menu items and tool bar items, and modifying events selection using the timeline
exit the event creation mode.
Triggering submenu items in the "Music" menu or the corresponding items in the tool bar
does not exit the event creation mode,
but the user cannot actually create events while the music is playing.
Triggering undo or redo in the case where the reverted action was made using event creation mode
does not exit the event creation mode.
Interaction with the timeline does not exit the event creation mode.
Interaction with the inspection panel does not exit the event creation mode.
[Flipping horizontally or vertically](#flip-horizontally-flip-vertically) does not exit the event creation mode.

For hold and bg note, the default duration is the same as the last time the user creates this type of event.
If this is the first time the user creates this type of event,
then the default duration is one beat.
For flick, the default direction is the same as the last time the user creates a flick.
If this is the first time, the default direction is being upward ($\pi/2$).

This submenu item grays out if the current channel is inactive
(which should only happen if all channels are inactive).

#### B&eacute;zier curve

Enters B&eacute;zier curve creation mode.
In this mode, clicking in the main editor field creates a control point for the new curve.
Already created control points can be moved by dragging with mouse.
The control points can snap (but not attach) to snappees.
Throughout the process, the new curve is drawn according to currently created control points.
To finish creating the curve, double click when creating the last control point,
or hit <kbd>Enter</kbd>.

#### Circular arc

Enters circular arc curve creation mode.
The first click sets the center.
The second click sets one end of the arc.
While the mouse cursor moves before the second click,
a translucent circle is drawn to indicate which circle the new arc will be on.
The third click sets the other end of the arc.
The other end of the arc is at the intersection between the cirle and the segment connecting the third click and the center.
While the mouse cursor moves before the third click,
the arc is drawn to indicate what the new arc will look like.
The three control points can snap (but not attach) to snappees.
The third control points can also snap to the second control point,
in which case the arc is just a circle, and the curve is set as a closed loop.

Notice that, before the third click, how the arc change while the mouse moves must be continuous when the span angle of the arc goes through $\pi$.
Otherwise, the user cannot choose between large curve ($>\pi$) and small curve ($<\pi$).
However, the change in the arc has to be discontinuous when the span angle goes through $2\pi$.

Individual control point actions are separate items in the history panel.

When the last point snaps to the first point, the curve is set as a closed loop.

Individual control point actions are separate items in the history panel.

#### Free transform

This enters the free transform mode for selected events.
For `group` events, their anchors and their directly or indirectly contained events are all transformed.
If some events are attached to snappees,
the whole snappees are also transformed (by editing their transformation matrix;
also the bounding box where the free transform control point lives should also enclose the full snappees).
This is basically the same feature as the free transform in Photoshop.
It supports translating, rotating, scaling.
Hitting <kbd>Enter</kbd> finishes and applies the transformation.
Hitting <kbd>Esc</kbd> aborts the transformation.

When doing free transform, there is a interactable handle shown as a crosshair circle
that the user can drag to change the anchor of the transformation.
The anchor is used as the center of rotation.
The anchor can be snapped to any one of the events in the transformed events,
any one of the four corners of the bounding box, the center of any one of the four edges of the bounding box,
and the center of the bounding box.
When it is snapped to the things above, the anchor moves together with the bounding box as it transforms.
The anchor can also snap to snap points on active snappees or not snap to anything,
and it does not move together with the bounding box in this case.
Initially, the anchor is snapped to the center of the bounding box.

When the user does a scaling by dragging a corner handle while holding <kbd>Ctrl</kbd>,
the scaling preserves aspect ratio.
When the user does a scaling by dragging a corner handle or an edge handle while holding <kbd>Shift</kbd>,
the scaling takes the anchor instead of the opposite handle as the fixed point.
When the user does a rotation while holding <kbd>Ctrl</kbd>,
the rotation snaps to integer multiples of $\pi/4$.

When translating/scaling/rotating,
if the transform makes some event out of the chart boundary, clamp the translation/scaling/rotation
so that the event that is about to be out of the boundary is exactly at the boundary.

If no events are selected but a snappee is selected,
transform this whole snappee.
Grayed out if neither any events nor any snappee is selected.

If the bounding box of the selected events is degenerate
(for example, if the selected events are two notes with the same x coordinate, in which case the bounding box is just a vertical line
but not a 2D box),
the free transform cannot start.

When doing the free transform, the inspection panel shows numbers for the transformation matrix.
Arrange the six number inputs as a 2&times;3 matrix following the CSS/Canvas affine convention:
$$
\begin{pmatrix}a&c&t_x\\ b&d&t_y\end{pmatrix}.
$$
The numbers update as the user does the transform.
The user can manually edit them.
Hitting <kbd>Enter</kbd> while editing a matrix element does not confirm the free transform
but submit an update in the matrix elements.

Notice that the `flick` events' directions should also change when doing the transform.
See source code of sscharter for example implementation.
The tip point spawn positions should also change.

#### Transformation matrix...

It is a 2D affine transform matrix, with 6 degrees of freedom,
so there are 6 input fields arranged as the same 2&times;3 CSS/Canvas matrix as in the inspection panel.

Notice that the `flick` events' directions should also change when doing the transform.
See source code of sscharter for example implementation.

#### Move forward, Move backward

#### Time dilation...

Show a popup form that asks the user to enter a rational scaling factor,
which will be called $k$ later in this paragraph.
There is also a checkbox asking whether durations are preserved.
Suppose that originally the $i$th selected event has time $t_i$ and end time $T_i$, measured in beats.
Then, after the transformation, if durations are not preserved, we have
$t_i\to k\left(t_i-t_0\right)+t_0$ and $T_i\to k\left(T_i-t_0\right)+t_0$;
otherwise if durations are preserved, we have
$t_i\to k\left(t_i-t_0\right)+t_0$ and $T_i\to k\left(t_i-t_0\right)+t_0+T_i-t_i$.
Here, $t_0$ is the time of the earliest selected event measured in beats.

This menu item is still functional even if there is no music loaded.

When the music is playing, also play note hit effects. Check `../game-unstable/js/ui/fx/*.js` for implementation.
The note hit effects should align with the one in Sunniesnow.
The hit effects disappear immediately when the music stops.

While music is playing, because the current time is not snapped to beat subdivisions,
many editor functions should be disabled.
You need to gray out most of them.

and set the playback rate while the music is playing.
Also, the editor functions that neither rely on quantized current time (e.g., creating events),
nor open popup forms (e.g., creating meshes),
nor enter dedicated editing modes (e.g., pen),

You need to schedule WebAudio nodes properly to achieve this perfection.
If the current time was originally in the visible range

The music does not actually play, so there will only be note SE and metronome (if enabled).

While the music is playing in reverse, the user operations that would be disabled during music playing are also disabled.
Reverse playing is almost identical to normal playing in terms of UX.

The note hit effects do not play when the music is playing in reverse.

If the current time was originally in the visible range
and the sudden change in the current time makes it outside the visible range,
change the visible range by minimal amount to make the current time inside the visible range.

## Event types

When a position is attached to a snappee, an icon identical to the one shown in the snappees panel is shown
to indicate which snappee it is attached to.

For all event types that has the "Duration" field, also add a "End time" field that accept a rational number,
whose value is equal to its time plus its duration.
The end time cannot be set to be smaller than the time.
If an event type does not allow zero duration,
the end time cannot be set to be equal to the time, either.
Whenever the user changes one of the duration and the end time,

When the user selects a bunch of events with durations and changes their end time altogether,

## Tip points

In sviber, there is no placeholder event, which is used in Sunniesnow for constructing arbitrary tip point paths.
Therefore, the tip point patterns that can be created in sviber is a strict subset of what Sunniesnow supports.
The only events that can be connected by a tip point are tap, hold, drag, and flick (i.e., all note events).
Note that bg notes are not tip-pointable in sviber although Sunniesnow supports connecting them with tip points.
Such events are called tip-pointable events.

Every tip-pointable event has some parameters that control how they are connected by tip points,
and the collection of those parameters are called the tip point mode of an event.
The tip point mode consists of the following parameters:

- Spawn type
- Absolute spawn position (two numbers; not editable if attached)
- Relative spawn position (two numbers, one number for distance and the other for direction)
- Time in seconds (one number)
- Time in beats (one rational number)

Radio inputs are used for choosing one from absolute and relative spawn positions.
Only one of them can be used, and the input fields of the other are hidden.
Radio inputs are used for choosing one from time in seconds and beats.
Only one of them can be used, and the input fields of the other are hidden.
The input fields for all tip point parameters except the spawn type are hidden if the spawn type is "inherit" or "none".

When changing the spawn type from inherit to chain or drop,
fill the other tip point parameters according to the spawn parameters that it inherited before if any.
Otherwise, fill with the default parameters.

When saving as Sunniesnow chart,
a placeholder event is generated for spawning the tip point.

### Tip point spawn type

The tip point spawn type is one of "inherit", "chain", "drop", and "none".
The default is "inherit".

If a tip-pointable event has the inherit spawn type, then:

- If the previous tip-pointable event in its channel has the chain spawn type,
  then this event is connected by the same tip point as the previous tip-pointable event.
- If the previous tip-pointable event in its channel has the drop spawn type,
  then this event is connected by a new tip point with the same spawn parameters (position and time) as the previous tip-pointable event.
- If this event is the first tip-pointable event in the channel
  or if the previous tip-pointable event has the none spawn type,
  then this event is not connected by a tip point.

If the next tip-pointable event in the channel also has the inherit spawn type,
then it sees the tip point spawn type of this event as the same spawn type of the previous tip-pointable event in the channel.

For example, suppose that the tip-pointable events in a channel have the following spawn types:
(1) inherit, (2) chain, (3) inherit, (4) inherit, (5) drop, (6) inherit, (7) inherit, (8) none, (9) inherit.
Then, the events 1, 8, and 9 are not connected by tip points.
The events 2, 3, and 4 are connected by the same tip point.
The events 5, 6, and 7 are connected by separate tip points
with the same spawn parameters.

The spawn types are inspired by [sscharter](https://github.com/sunniesnow/sscharter).
Read its source code for more information.

There is the edge case of multiple simultaneous tip-pointable events being in the same channel,
in which case it is hard to determine which one is previous and which one is next.
Just ignore this quirk and take whatever order that is already present in the data structure as the order of the simultaneous events.
Depending on the order of simultaneous events in the same channel for tip point behaviors
is undefined behavior,
and users are discouraged to do that.

### Spawn position

The spawn position can either be absolute or relative.

The absolute spawn position is either directly the coordinates that set where the tip point will spawn,
or attached to a snappee for the position.

The relative spawn position is set by the distance and direction of the spawn.
This specifies the spawn position relative to the first event that the tip point connects to.
For example, if the spawn position is 100 with the direction of $\pi/2$,
then it spawns above its first event with 100 distance from it.

The default spawn position is relative, 100, $\pi/2$.

These fields are grayed out if the spawn type is not drop or chain.

### Spawn time

The spawn time specifies when the tip point spawns.
It can either be specified in seconds or specified in beats.
For example, if it is set to 1 second, then the tip point spawns at 1 second before the time of the first event that it connects to.
If it is set to 2 beats, then the tip point spawns at 2 beats before the time of the first event that it connects to.

The default spawn time is 1 second.

These fields are grayed out if the spawn type is not drop or chain.

## Live hosting

Live hosting is the feature that sets up a server for Sunniesnow to connect to
for play testing and using Sunniesnow's feature to debug the chart.
All functions related to live hosting can only be used in the NW.js app
and are disabled in browser webpage.

There are ports that the live hosting server listen to, one for hosting the level file with HTTP,
and the other for pushing updates to Sunniesnow (also called live reload) with web socket.
The protocol that the latter feature uses is sscharter,
with the same name as the charting tool
[sscharter](https://github.com/sunniesnow/sscharter) that solidified this protocol.

The HTTP port simply serves a Sunniesnow level file
that can be accessed with the address `http://${host}:${port}/sviber.ssc`,
where `host` and `port` are set in editor preferences.
To reduce performance burden,
the level file has level-zero compression and is only present in the memory instead of in the disk.

The sscharter protocol is a socket connection with JSON messages.
For a client-side implementation, see `../game-unstable/js/external/Sscharter.js`.
For a server-side implementation, see in the source repo of sscharter `lib/sscharter/cli.rb`.
You need to support all types of messages except the `eventInfoTip` message, which you simply ignore.
The feature of sscharter protocol is enabled only if the live reload port is set to a nonzero value in editor preferences.

When the live reload feature is enabled, charts JSON will have an `sscharter` field;
otherwise they do not have the field.
The `version` field in the `sscharter` object is set as the version of `sscharter` whose implementation you looked at.

When the live hosting server starts, put a toast message containing information about
the host, port, and live reload port.
When there is an error about the live hosting, put a toast message about the error.
When the live hosting server ends, put a toast message saying that.

## Macros interface

The macros interface is a separate webpage from sviber, and it needs to communicate with sviber.

### Macros API

You need to implement a JavaScript API and a Ruby API that codes in macros can use to modify sviber's state.
The JavaScript and Ruby codes that implement the API and the HTML for the sandbox iframe
should be put in separate files instead of inline strings.

You need to write detailed documentation of the API with full examples in the user manual.

Here I give an overview of the API in Ruby conventions.
If you need to additionally define functions or classes not mentioned in this section,
they should not be meant for the user to use.
JavaScript API should have similar interface.
The API defined in [sscharter](https://github.com/sunniesnow/sscharter) inspired this API.
You can refer to the source code of sscharter when implementing similar functions.

Notice that Ruby has native rational number support,
so all beat data should only accept `Integer` and `Rational`.
For JavaScript, accept number (quantized using a set maximum denominator),
two numbers array (numerator and denominator of a rational number),
and three numbers array (the rational 3-tuple used in [file format](#file-format)).

Because Ruby uses underscore convention while JavaScript uses camel case convention,
a conversion is needed when using Ruby symbols.
For example, the `#type` of a `bgNote` event is `:bg_note` in Ruby instead of `:bgNote`.

For any function argument that means an angle, it can accept either a number representing the angle in radians,
or a symbol (for JavaScript, string)
among `:up` (equivalent to `:u`), `:left` (equivalent to `:l`),
`:right` (equivalent to `:r`), `:down` (equivalent to `:d`),
`:up_left` (equivalent to `:left_up`, `:ul`, `:lu`), etc.

For any function argument that means a color, it can accept a hex number or any color format that CSS accepts.
It is converted to the standard format.

Placing events and transforming events never check whether event positions are within the chart boundary.

The `#delete` methods for most classes make them unable to be operated further.
For example, calling `channel.select` after `channel.delete` raises an error.

- `t(location, text="")`: equivalent to `Tap::new(location:, time: Chart::current_time, channel: Channel::current, text:)`.
- `h(location, duration, text="")`: equivalent to `Hold::new(...)`.
- `d(location)`: equivalent to `Drag::new(...)`.
- `f(location, angle, text="")`: equivalent to `Flick::new(...)`.
- `bg_note(location, duration=0, text="")`: equivalent to `BgNote::new(...)`.
  When only one of `duration` and `text` is omitted, determine which one is omitted by inspecting the data type.
- `big_text(duration, text="")`: equivalent to `BigText::new(...)`.
- `grid(duration)`, `diamond_grid(duration)`, `hexagon(duration)`, ...
- `g(events, color=nil)`: equivalent to `Group::new(...)`.
- `g(color=nil, &block)`: all events added while executing `block` are added to a group event and then return the group.
- `copy(events)`: copy events in `events` and paste at the current time and current channel. This does not modify system clipboard or the chart's clips. Return the array of new events.
- `transform(things, matrix)`: make an affine transformation; `things` can be an event, a snappee, array of events, or array of snappees.
- `transform(things, &block)`: equivalent to
  `transform(things, AffineMatrix2D.new.tap { _1.instance_eval &block })`.

## File format

This section explains the chart file format of sviber.
When updates are made in this section, do not concern with backward compatibility when you make modifications to sviber accordingly.

The file format saved by sviber is an extension to Sunniesnow's chart file format.
Sunniesnow's chart file format is documented in `../doc/chart.md`.
As an extension, the sviber chart format has an additional key at the top-level JSON object called `sviber`,
which is an object containing all the information that is required for charting using sviber
(except some metadata, including `title` etc., which are simply present in the original Sunniesnow chart format).

The JSON object under the key `sviber` is an object containing the following properties:

- `music`: the path to the music file.
- `image`: the path to the image file (often used as background).
- `editor`: an object containing information of editor status that does not relate to the actual chart,
  such as the current time and the current channel.
- `timing`: an object containing timing information, such as offset and BPM.
- `channels`: an array of objects containing information of channels.
- `events`: an array of objects containing information of events,
  including notes, `bgNote` events, and background patterns.
- `snappees`: an array of objects containing information of snappees.

When saving a chart using sviber,
the top level `events` field will be generated to ensure Sunniesnow compatibility.
That field is useless for sviber.
When generating the `events` field, do not include events in inactive channels.
The events are ordered according to the channels,
with events in the channel ordered at the first being put in the generated array at the first.
For simultaneous events in the same channel,
their order matches the order of stacking as appearing in the timeline interface,
with the event stacked at the top being ordered at the first.

Sometimes one needs to represent a rational number in JSON.
It is represented as a 3-tuple of numbers,
the 3 numbers respectively being the integer part, the numerator of the frational part,
and the denominator of the fractional part.

This file format may not be optimal. Improve it if you think you have better ideas.

### `music` field and `image` field

These two fields are file paths in the local filesystem.
They are useless on the live webpage because normal browser does not allow accessing local files.
However, for the NW.js app, there is API for accessing local files.
In this case, loading chart with this information will automatically load specified music file and image file.

### `editor` field

A JSON object with the following fields:

- `timeSnapped`: whether the current time is snapped to subdivisions.
- `subdivision`: the current subdivision, a positive integer. Integer $n$ means that the subdivision is $1/n$.
- `currentTime`: either a float number if `timeSnapped` is false or a rational number 3-tuple denoting the current time in beats.
- `currentChannel`: channel ID of the current channel.
- `visibleRangeBeginning`: float number indicate the visible range start.
- `visibleRangeEnd`: float number indicate the visible range end.
- `timelineChannelOffset`: the vertical scroll position of channels in the timeline.
- `speed`: playback rate.
- `lockVisibleRange`: boolean.
- `playSe`: boolean.
- `seekBackAfterPlaying`: boolean.
- `metronome`: boolean.
- `abLoopMarks`: array of either one or two rational 3-tuples.
- `allowOutOfBound`: boolean.
- `showGroupingInTimeline`: boolean.
- `showGroupingInMainField`: boolean.
- `showTipPoints`: boolean.
- `mainFieldPanX`: number.
- `mainFieldPanY`: number.
- `mainFieldZoom`: number.

### `timing` field

A JSON object with the following fields:

- `offset`: float number, time of beat 0.
- `initialBpm`: initial BPM, the BPM before the first BPM change.
- `bpmChanges`: an array of BPM changes.
- `barLines`: an array of bar lines.

Each BPM change is a JSON object with the following fields:

- `time`: rational 3-tuple representing time in beats.
- `bpm`: float number for the BPM value.

Each bar line is a JSON object with the following fields:

- `time`: rational 3-tuple representing time in beats.

### `channels` field

An array of channels. Each channel is a JSON object with the following fields

- `id`: an integer ID number. It increments starting from 0, to distinguish different channels.
- `name`: string, the user-set name.
- `active`: boolean, whether it is active.

When moving channels around (e.g., [move channel up and move channel down](#move-channel-up-move-channel-down)),
the ID number of the channels do not change,
but they only change order in this array.

### `events` field

An array of events.
Each event is a JSON object with the following fields (nonexhaustive):

- `type`: string, one of `tap`, `hold`, `flick`, `drag`, `bgNote`,`bigText`,
  `grid`, `hexagon`, `checkerboard`, `diamondGrid`, `pentagon`, `turntable`, `hexagram`, `comment`, `group`.
- `selected`: boolean, whether it is selected.

Other fields depend on the type.

Events except `group` have the following fields:

- `time`: rational number 3-tuple indicating the time in beats.
- `channel`: channel ID number.

Movable events (`tap`, `hold`, `flick`, `drag`, `bgNote`, `group`) have these fields:

- `attached`: boolean, whether attached to a snappee.
- `x`: x coordinate, present if `attached` is false.
- `y`: y coordinate, present if `attached` is false.
- `snappee`: snappee ID number indicating which snappee it is attached to, present if `attached` is true.
- `snapPoint`: either one number `i` if the snappee is a curve,
  or two numbers `[i,j]` if the snappee is a mesh; present if `attached` is true.

Events with durations (`hold`, `bgNote`, `bigText`,
`grid`, `hexagon`, `checkerboard`, `diamondGrid`, `pentagon`, `turntable`, `hexagram`, `comment`)
have these fields:

- `duration`: rational 3-tuple denoting the duration in beats.

Events with texts (`tap`, `hold`, `flick`, `bgNote`, `bigText`, `comment`) have these fields:

- `text`: arbitrary string for the text.

`flick` events have these fields:

- `angle`: direction denoted as an angle in radians.

Tip-pointable events (`tap`, `hold`, `drag`, `flick`) have these fields:

- `tipPointSpawnType`: string, one of `inherit`, `chain`, `drop`, `none`.
- `tipPointSpawnAbsolutePosition`: boolean.
- `tipPointSpawnAttached`: boolean, present if `tipPointSpawnAbsolutePosition` is true.
- `tipPointSpawnX`: x coordinate of spawn position,
  present if `tipPointSpawnAttached` is present and false.
- `tipPointSpawnY`: y coordinate of spawn potision,
  present if `tipPointSpawnAttached` is present and false.
- `tipPointSpawnSnappee`: snappee ID,
  present if `tipPointSpawnAttached` is present and true.
- `tipPointSpawnSnapPoint`: either one number `i` if the snappee is a curve,
  or two numbers `[i,j]` if the snappee is a mesh;
  present if `tipPointSpawnAttached` is present and true.
- `tipPointSpawnDistance`: number for the spawn distance,
  present if `tipPointSpawnAbsolutePosition` is false.
- `tipPointSpawnAngle`: number for spawn direction, angle in radians,
  present if `tipPointSpawnAbsolutePosition` is false.
- `tipPointSpawnTimeBeats`: boolean.
- `tipPointSpawnTime`: either rational 3-tuple specifying relative spawn time in beats if `tipPointSpawnTimeBeats` is true,
  or a float number specifying in seconds otherwise.

Finally, `group` events have the following fields:

- `events`: a list of events in the same format of `sviber` object's `events` field. Events in a group are not repeated outside the group.
  It may contain any type of events, including `group` events.

### `snappees` field

An array of snappees.
Each snappee is a JSON object with the following fields:

- `id`: ID number.
- `name`: user-set name.
- `color`: color in CSS hash plus hex format.
- `type`: string, one of `rectangularMesh`, `radialMesh`, `parametricMesh`,
  `regularPolygonCurve`, `bezierCurve`, `circularArcCurve`, `penCurve`, `parametricCurve`.
- `transformation`: a 6-number array denoting an affine transformation matrix.
- `active`: boolean, whether it is active.
- `selected`: boolean, whether it is selected.

Other fields depend on the type.

For rectangular mesh:

- `topLeftX`: top left x coordinate.
- `topLeftY`: top left y coordinate.
- `bottomRightX`: bottom right x coordinate.
- `bottomRightY`: bottom right y coordiante.
- `horizontalTiles`: number of tiles in x direction.
- `verticalTiles`: number of tiles in y direction.

For radial mesh:

- `centerX`
- `centerY`
- `radius`
- `azimuthalTiles`
- `radialTiles`

For parametric mesh:

- `iRange`: array of two integers indicating the range of `i`.
- `iRangeExclusive`: boolean, whether the upper bound of `iRange` is exclusive.
- `jRange`
- `jRangeExclusive`
- `xExpression`: string of mathematical expression.
- `yExpression`

For regular polygon curve:

- `centerX`
- `centerY`
- `angle`
- `radius`
- `segmentsPerSide`

For B&eacute;zier curve:

- `degree`
- `controlPoints`: array of `{x:,y:}` objects.
- `segments`: integer, number of segments.

For circular arc curve:

- `centerX`
- `centerY`
- `radius`
- `closed`: boolean, whether a closed loop.
- `beginningAngle`
- `endAngle`: only present if `closed` is false.
- `clockwise`: whether the arc is drawn from beginning angle to the end angle in the clockwise direction.
- `segments`

For pen curve:

- `commands`: the curve commands. You invent your own data structure. Make it readable by human as possible.
- `segments`
- `closed`: depending on how you decide the data structure for `commands`, this field may be unnecessary.

For parametric curve:

- `iRange`
- `iRangeExclusive`
- `xExpression`
- `yExpression`
- `closed`

### `clips` field

An array of clip objects.
Each clip object has the following field:

- `name`
- `data`: the same structure as clipboard data when copying events.

## Lyrica chart format

Lyrica is the rhythm game that Sunniesnow is inspired from.
You can refer to [sunniesnow-convert](https://github.com/sunniesnow/sunniesnow-convert)'s source
the file `lib/sunniesnow-convert/converters/lyrica.rb` for how a Lyrica chart is converted to a Sunniesnow chart.
However, you need to implement direct conversion between sviber chart and Lyrica chart,
not using a Sunniesnow chart as medium.
Especially, you never need the concept of placeholder events when converting between Lyrica chart and sviber chart.

A Lyrica chart file is a text file of this format:

```
[header]
#1
[data]
#2
[data]
#3
[data]
#4
[data]
```

The hashed numbers are not actually meaningful.
However, legitimate charts always put events in channels from `-100` to `20` under `#1`,
events in channels from `40` to `100` under `#2`,
events in channels from `120` to `180` under `#3`,
and events in channel `200` under `#4`.

`[header]` is a line of text in the format explained in [Lyrica chart header](#lyrica-chart-header).
`[data]` is a line of text that is a comma-separated list of events,
each of which is in the format explained in [Lyrica events](#lyrica-events).

### Lyrica chart header

The header is one line of text.
The header fields are separated by pipeline characters (`|`).
For example, a header can be

```
199|rainbow|ああああ|0.6029994|4|0
```

The meaning of header fields are listed below with the listed order:

| Meaning | Data format | Example | Possibly absent? |
|-|-|-|-|
| Initial BPM | Number | `199` | No |
| Title | String | `rainbow` | No |
| Artist | String | `ああああ` | No |
| Offset | Number | `0.6029994` | No |
| Time signature | Number | `4` | Yes |
| BPM changing check mode | `0` or `1` | `0` | Yes |

You can safely ignore time signature and BPM changing check mode for any purposes related to sviber.
The other fields have the same meaning as in sviber, so no need for further explanations.

### Lyrica channels

A legitimate Lyrica chart always has no channels other than those listed below:

| Channels | Category | Feature |
|-|-|-|
| `-100`, `-80` | No-tip-point channel | Notes here do not have tip points. |
| `-60` | Main channel | Notes here may be used as tip point spawn positions. |
| `-40`, `-20`, `0` | Normal channel | Notes. |
| `20` | Independent channel | Every note is connected by its own tip point. |
| `40` | Bg patterns channel | Bg patterns. |
| `60`, `80` | Bg notes channel | Bg notes. |
| `100`, `120`, `140`, `160`, `180` | Disabled channel | Events are useless. |
| `200` | BPM changes channel | Events mean BPM changes. |

### Lyrica events

The data for each event in a Lyrica chart is written as pipeline-separated fields.
The fields are listed in the following table, with the listed order:

| Field | Data format | Example | Possibly absent? |
|-|-|-|-|
| Time in seconds | Number | `0.3571429` | No |
| Channel | Integer | `60` | No |
| X | Number | `-75` | No |
| Y | Number | `-50` | No |
| Type | Integer | `13` | No |
| Argument | Underscore-separated numbers | `1_0` | No |
| Text | String | `不` | No |
| Tip point spawning | Integer | `0` | No |
| Tip point ending | `0` or `1` | `0` | Yes |
| Anomalous properties | Integer | `0` | Yes |

For all purposes related to sviber,
you can safely ignore the anomalous properties.

The actual type of an event is determined by the channel and the type number,
and the meaning of the argument is determined by the actual type.
The rest of this section gives tables that tell you how to determine the event types according to the channel and the type number.
Some legitimate charts have events whose type numbers are not in the tables for their channels,
and you should ignore those events.

In the no-tip-point channels, the main channel, the normal channels,
and the independent channel,
these are the event types:

| Type number | Type | Argument meaning |
|-|-|-|
| `0` | Drag | |
| `1` | Tap | Solo tap |
| `2` | Tap | Simultaneous tap (多押); official charts use this when two or more taps share a time |
| `3` | Flick | Angle in degrees (zero is upward, clockwise) |
| `4` | Hold | Duration in seconds |

In the bg patterns channel, these are the event types:

| Type number | Type | Argument meaning |
|-|-|-|
| `4` | Any of the bg pattern types | Duration in seconds |

The text of a bg pattern determines which bg pattern it is:

| Text | Bg pattern type |
|-|-|
| `a1` | Grid |
| `a2` | Hexagon |
| `a3` | Checkerboard |
| `a4` | Diamond grid |
| `a5` | Pentagon |
| `a6` | Turntable |
| `a7` | Hexagram |
| Others | Big text |

The text is the actual text of the big text event if it does not make the event one of the other bg pattern types.

In the bg notes channels, these are the event types:

| Type number | Type | Argument meaning |
|-|-|-|
| `0`, `1`, `2`, `3` | Bg note | |
| `4` | Bg note | Duration in seconds |
| `11` | Show image | Duration in seconds, image ID |
| `12` | Half role image | Duration in seconds, image ID |
| `13` | Filter | Duration in seconds |

Only the bg notes with type `4` can have nonzero durations.
For any purpose related to sviber,
you can safely ignore the types `11`, `12`, and `13`.

Events in disabled channels are useless.

In the BPM changes channel, these are the event types:

| Type number | Type | Argument meaning |
|-|-|-|
| `4` | BPM change | Ratio of the BPM immediately after the time of this event to the initial BPM |

### Tip point mechanics in Lyrica

Only and all events in the main channel, the normal channels, and the independent channel are connected by tip points in Lyrica.
This section only applies to events in those channels.

How events are connected by tip points and how the tip points are spawn
are determined by the channels, the tip point spawning parameter (denoted as $b$),
and the tip point ending parameter (denoted as $c$).
For events whose $c$ is missing, define
$$b'=(b\bmod10)+20\left\lfloor\frac b{20}\right\rfloor,\qquad
c'=\left\lfloor\frac{b\bmod20}{10}\right\rfloor,$$
and then use $b'$ and $c'$ as the actual parameters.

If the value of $b$ is not covered in the table below,
regard it as $b=0$.

If an event is the first event that a tip point connects to,
the position and time at which the tip point spawns is determined
according to the following table.

| $b$ | Spawn x | Spawn y | Spawn time |
|-|-|-|-|
| 0 | If in the independent channel and `x1` exists, `x1`; otherwise, `x > 0 ? clamp(x-120,-100,0) : clamp(x+120,0,100)` | If in the independent channel and `y1` exists, `y1`; otherwise, `rand(-50,50)` | `t - 1.5` |
| 1 | If `x1` exists, `x1`; otherwise, `x > 0 ? clamp(x-120,-100,0) : clamp(x+120,0,100)` | If `y1` exists, `y1`; otherwise, `rand(-50,50)` | If in independent channel or `t1` does not exist, `t - 1.5`; otherwise, `t1` |
| 2 | `x > 0 ? clamp(x-120,-100,0) : clamp(x+120,0,100)` | `rand(-50,50)` | `t - 1.5` |
| 3 | `rand(clamp(x-40,-130,130), clamp(x+40,-130,130))` | `y > 0 ? -75 : 75` | `t - 1.5` |
| 4 | `(abs(x)>50 ? x>0 : rand_bit) ? clamp(x-120,-100,0) : clamp(x+120,0,100)` | `rand_range -50, 50` | `t - 1.5` |
| 4 | `rand(clamp(x-40,-130,130), clamp(x+40,-130,130))` | `-80*(abs(x) > 50 && abs(y) > 20 ? sgn(y) : (-1)**rand_bit))` | `t - 1.5` |
| 5 | `x > 0 ? clamp(x-120,-100,0) : clamp(x+120,0,100)` | `y` | `t - 1.5` |
| 6 | `x` | `y > 0 ? -100 : 100` | `t - 1` |
| 20 | `x` | `y - 100` | `t - 1` |
| 21 | `x - 72` | `y - 72` | `t - 1` |
| 22 | `x - 100` | `y` | `t - 1` |
| 23 | `x - 72` | `y + 72` | `t - 1` |
| 24 | `x` | `y + 100` | `t - 1` |
| 25 | `x + 72` | `y + 72` | `t - 1` |
| 26 | `x + 100` | `y` | `t - 1` |
| 27 | `x + 72` | `y - 72` | `t - 1` |

If there are multiple rows for the same value of $b$, one of them is randomly selected.
The functions and variables referenced in the table are:

| Variable/function | Meaning |
|-|-|
| `x` | The x coordinate of this event |
| `y` | The y coordiante of this event |
| `t` | The time in seconds of this event |
| `x1` | The x coordinate of the latest event in the main channel before (exclusive) this event |
| `y1` | The y coordinate of the latest event in the main channel before (exclusive) this event |
| `t1` | The time in seconds of the latest event in the main channel before (exclusive) this event |
| `rand_bit` | A random zero-one value or a random boolean value |
| `rand(u,v)` | A random float between `u` and `v` |
| `clamp(u,v,w)` | Return `v` if `u<v`; return `w` if `u>w`; return `u` otherwise |
| `abs(u)` | Absolute value |
| `sgn(u)` | Sign, one of -1, 0, 1 |

After looking up the spawn time from the table,
if this event is not in the independent channel,
the spawn time needs to be clamped
so that it is at least `t - 2` and is at least the time of the previous event in the same channel before this event.

If an event is not the first event that a tip point connects to,
it is connected by the same tip point as the previous event in its channel.
An event is the first event that a tip point connects to if at least one the following conditions is met:

- This event has nonzero $b$ covered in the table.
- There are no events earlier than this event in its channel.
- This event is in the independent channel.
- This event is more than 2 seconds after the previous event in its channel.
- The previous event in the channel has nonzero $c$.

### Number input

Number input is common in many popup forms.

Nonnegative rational numbers are used for beat numbers.
A rational number should be input using three integer input fields,
meaning the integer part and the numerator and the denominator of the fractional part.
The HTML can be `<input>+<input>/<input>`.
Because the integer part is often 3 digits
but the numerator and the denominator of the fractional part are almost never longer than 2 digits,
the integer part input should be a larger box than the other two.

Values check of the input (e.g., numerator must be smaller than denominator, and numerator and denominator must be coprime)
happens only after the user finishes changing all three inputs.
If the values check happens immediately after one input changes, it is impossible to change, for example, 1+0/1 into 1+1/2
(Want to change numerator first? No, numerator must be smaller than denominator.
Want to change denominator first? No, numerator and denominator must be coprime.).
Also, the numerator and denominator not being coprime does not make the input unacceptable,
but it should be automatically converted to reduced fraction.

Number input for coordinates should generally accept mathematical expressions.
They are parsed by math.js.

Number input for angles should have an accompanying checkbox for whether radians mode is on.
The radians mode should be off by default.
In either case, the number input should accept math expressions.

Range input for integer parameters (for creating and editing parametric snappees) consists of two integer number inputs.
There should also be an accompanying checkbox to choose whether the upper bound is inclusive or exclusive.
It should be exclusive by default.
